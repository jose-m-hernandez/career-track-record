## 1. Purpose

Read one version of a career document through several named lenses, each a model reader in a stated role such as recruiter, hiring manager or peer, and report whether it passes a condition written before the first read, without letting the person running the test move the goalposts after seeing the answer, and without counting a lens that cannot tell a strong document from a weak one.

`track-record ab` compares two versions and asks which reads better. This command is the single-version cold read that docs/specs/reader-ab.md § 2 lists as out of scope and § 9.4 plans. It follows rule 6 of the method ("Test before you trust"): every lens carries its own control, so a lens that shows nothing also shows whether it was able to see something. Known limit: a lens that passes its anchor gate can tell the strong anchor from the weak one; that does not show it could see a difference as small as one between this version and another.

## 2. Scope

In scope:

- blind reads: a reader in a given role sees one posting, one lens file and one document, and scores the document alone;
- lenses: each is a plain-text prompt file the user writes, named in the plan and frozen with it;
- the anchored rubric: two planted documents the user supplies, a deliberately strong one and a deliberately weak one, read through every lens in every run;
- the anchor gate: a lens that does not put the strong anchor at or above one threshold and the weak anchor at or below another has its reads of the version reported INCONCLUSIVE and not counted;
- the headroom check: whether the instrument can score above the version, from the strong anchor's scores against the version's over several reads (revision 4);
- calibration: an optional anchors-only run that fixes a lens before any version is read (revision 4);
- preregistration: the pass conditions, per lens and overall, frozen by hash before the first read;
- replicate runs: the same frozen plan run again in a new folder, compared with the first run;
- scoring the replies against the frozen rules, and writing a result;
- the evidence beside each verdict: an interval for each clause count, an exact p-value when a rule names a share to test against, the reads that are missing, and what the scores can and cannot show (§ 6.1).

Out of scope:

- writing or rewriting copy (readers may suggest rewrites; the tool never applies one);
- deciding what is true (a reader's doubt is a lead; the user's own record decides);
- comparing two versions (that is `ab`);
- recall tests (which of several versions a reader remembers), version ledgers, and any change to `claims`, `barred`, `tone` or `keywords`;
- supplying anchors: the tool ships invented anchors as test fixtures only, and a user writes their own, for their own posting;
- any network call from the test suite.

## 3. Inputs

### 3.1 The plan file

The plan is a plain-text file in the syntax of `ab` (reader-ab.md § 3.1 and its build interpretations): each line is `key: value`; a list value is one item per indented line under its key, with fields separated by ` | `; blank lines and lines starting with `#` are ignored; an unknown key, a repeated key or a field that holds ` | ` is an error (exit `2`). The plan names:

- `posting`: the posting file;
- `version`: the one document under test;
- `anchors`: two items, `strong | <file>` and `weak | <file>`, each exactly once. From revision 4, each also says who wrote it, required, as `| written-by <who>`, and may then add `| note <text>`, free text. The note is the item's last field, and its text runs to the end of the line, ` | ` included, an exception to the rule above. `<who>` is one of: `user`, when no model wrote or edited a word of it; `model <family>`, naming every model family that wrote or edited any of its wording, not only the last editor, with more than one written as a comma list (`model <family>, model <family>`); `third-party`, a person other than the user; or `unknown`. The result header prints both;
- `lenses`: each lens's name and its prompt file (§ 3.3), `<name> | <file>`, and optionally `max <n>`, the top of the lens's own scale, a whole number at or above `anchor-strong-at-least` (§ 6.1). Names are letters, digits and `-`, unique, and not one of the words `all`, `overall`, `strong`, `weak` or `version`. The result names lenses `l1`, `l2` and so on in plan order. From revision 4, each lens also carries `author-edited-version yes` or `author-edited-version no`, required: `yes` when whoever wrote the lens's rubric, a person or a model, also wrote or edited the version under test. It is about the version only, not every document in the plan; who wrote the anchors is recorded by `written-by`. It is a disclosure: the result prints it, and it changes no verdict. A lens may also carry `criteria <A>,<B>,...`, the names of the criteria its rubric scores (§ 5.4, § 6);
- `readers`: each reader's name and command, and optionally `not-blind`, `cost <n>` and `reader-group <name>`, exactly as in `ab` (§ 5.1, § 5.5);
- `min-valid-reads` (optional): the read floor, a whole number, 1 or more. A rule that counts fewer valid reads from blind readers is INCONCLUSIVE (§ 6);
- `replicate-of` (optional): the freeze file of a first run of this same plan (§ 3.2);
- `reads-per-reader`: reads of the version per lens for each reader (default 3);
- `anchor-reads-per-reader`: reads of each anchor per lens for each reader (default 2 from revision 4; it was 1). Two readers then give 4 reads of each anchor per lens. The headroom check needs at least 3 valid reads of the strong anchor on a lens (§ 6). So the default run makes twice the anchor reads it did, and the anchor gate, which fails on one read on the wrong side, has twice the reads that can fail it. With one blind reader, the default gives 2 reads of the strong anchor, so headroom is not assessed: such a plan must set `anchor-reads-per-reader` to 3 or more;
- `calibration-only` (optional): `yes` makes the run read the anchors through every lens and read no version (§ 6, Calibration);
- `calibration` (optional): the freeze file of a calibration run of this plan's lenses (§ 6, Calibration). A run that reads the version and names none reports its scores as uncalibrated;
- `extends` (optional): the freeze file of a first run whose sample size this plan extends (§ 3.2);
- `anchor-strong-at-least` and `anchor-weak-at-most`: the gate's thresholds, whole numbers of any sign, both required, with the first greater than the second (§ 6);
- `rules`: each a pass condition for one lens or for the panel, `<lens> | <rule>` or `overall | <rule>`, in the clause language of § 6, and optionally `| null-share <n>/<d>`, the share of reads expected to pass each of its tests by chance, strictly between 0 and 1 and written as a fraction in no other form (§ 6.1). For example, `recruiter | PASS if score at least 7 in 5 of 6; FAIL if score at most 4 in 2 or more; otherwise INCONCLUSIVE`;
- `sidedness` (optional): `two`, `greater` or `less`, the side of the exact test against a rule's `null-share` (default `two`);
- `spend-ceiling`: the run's limit, in the plan's one spend unit (absent means no ceiling);
- `read-timeout`: seconds per live read (default 600);
- `fake-reader` (optional): the fake reader's rules (§ 5.3);
- `amends` (optional): the freeze file of the plan this one replaces (§ 3.2).

### 3.2 Freeze

`track-record panel freeze PLAN` hashes the plan and every input it names (sha256): the posting, the version, both anchors, every lens file and any amended freeze, plus the built-in prompt in each form the plan's lenses use (§ 5.4). It writes the hashes to a freeze file beside the plan and exits `0`. The rules of reader-ab.md § 3.2 hold unchanged: it refuses (exit `2`) a missing input, an existing freeze file or a run folder that already holds a reply; a run checks every hash first and exits `2`, naming the file, if any one differs, the plan and the lens files included; the run folder is the folder that holds the plan; an amendment is a new plan in a new run folder whose `amends` names the earlier freeze file, and the earlier folder is never edited. A replicate follows the rules of reader-ab.md § 3.2 for replicates: a new run folder whose `replicate-of` names a first run's freeze file, a plan byte-identical to the first apart from that line, every input (the lens files included) at the hash the first freeze recorded, and the first folder read, never written. An extension follows reader-ab.md § 3.2 for extensions, from revision 4: a new run folder whose `extends` names a first run's freeze; it may change the sample size only (`reads-per-reader`, `anchor-reads-per-reader` and the number of readers of the models that already read); every decision rule, threshold (`anchor-strong-at-least`, `anchor-weak-at-most`, each rule's bars and `null-share`), `sidedness`, `min-valid-reads`, document, lens and prompt must be as the first plan has them, and `freeze` refuses any other difference with exit `2`, naming the changed setting. Its verdicts pool the first run's reads with its own. On pooled reads, each count in a rule is read at its share of the planned reads. With P the number of pooled version reads the rule would count when every planned read is valid, and N the number the first plan's rule would count, `<k> of <m>` holds when exactly P reads are counted and at least k/m of P pass the test, and `<k> or more` holds when at least k/N of P pass it, however many are counted. So `6 of 6` is all of them, and `4 or more` of 6 planned is two thirds or more: a `<k> or more` rule does not get easier because more reads were pooled. `freeze` refuses the extension (exit `2`, naming the rule) when a count read at its share of P is not a whole number. Its result names the first freeze, says that the sample size changed after a result was seen, and prints the first run's verdict beside the pooled one. A first run can be extended once.

From revision 4, an amendment may change the read counts, never a threshold or a rule's bars. A rule's count is part of its threshold, as a share. So an amendment that changes the number of version reads a rule counts when every planned read is valid must restate each count in that rule at the same share: `6 of 6` becomes `12 of 12`, and `4 or more` of 6 becomes `8 or more` of 12. `freeze` compares the shares as exact fractions and refuses (exit `2`, naming the rule) when they differ, or when the new read count does not give a whole number. The rule text may change only in that way.

From revision 4, the freeze file records the spec revision it was frozen under, and a freeze file with no such record is treated as frozen under an earlier revision. A plan frozen under an earlier revision is refused at `run` and at `score` (exit `2`), and is never rescored under revision 4.

From revision 4, when the plan names a `calibration`, `freeze` refuses (exit `2`, naming the lens) a plan in which a lens file does not have the hash that the named calibration recorded for the lens of that name, or names a lens the calibration recorded no hash for.

### 3.3 Documents and lens files

The posting, the version and the anchors are UTF-8 text, or PDF read through the same text extraction the barred check uses. A lens file is UTF-8 text that is not blank. It is given to the reader as it is, as `LENS.txt`; the tool reads nothing into it and substitutes nothing in it. File names are free. **The lens owns its scale.** A lens may define its own scale and criteria, for example five criteria each scored 0 to 2 and summed to 0 to 10; the plan's thresholds and rules are written on that scale. The tool fixes no scale: any whole number is a valid `SCORE` (§ 5.4), 0 included.

## 4. Documents and the document check

### 4.1 What a reader sees

Each read is of one document. Within a lens, reads are numbered in the order they run: every reader's reads of the strong anchor, then of the weak anchor, then of the version. The reader sees `DOCUMENT.txt`, never the document's name or role: nothing in its folder says whether it is reading an anchor or the version. The key file, written before any read runs, maps each read to its document.

### 4.2 The document check (before any read)

The three documents are compared line by line after collapsing runs of spaces and dropping blank lines, as in reader-ab.md § 4.2. If any two of them show no changed line, the run stops before reading and exits `2`, naming the pair, because a gate between two copies of one text can tell nothing. A lens file that cannot be read, or is blank, stops the run the same way.

## 5. Readers

### 5.1 Pluggable

As in `ab`: a reader is a command the tool runs once per read; the read folder is its only input and one reply file is its output. The tool ships one reader that needs no network, the fake reader (§ 5.3). Live readers are configured by the user and are never shipped with credentials.

### 5.2 Live runs and run order

The test suite and CI never start a live reader. The `--live` rule of reader-ab.md § 5.2 holds unchanged: for a live run the tool prints the exact commands and the spend estimate, runs them only when the user types `--live`, and without it prints, starts nothing, writes no reply and exits `0`. A plan with any live reader and no `--live` runs nothing, fake reads included; a plan whose readers are all `fake` never needs `--live`.

Lenses run in plan order. Within a lens the anchors run first, strong then weak, and the version last, so that a run cut by the spend ceiling keeps its gate. The ceiling stops the run between reads once the tally of declared costs reaches it; reads already returned are kept, and the result says the run was cut.

### 5.3 The fake reader

The fake reader is a deterministic program for tests, run inside the tool, that applies to every reader whose command is the word `fake`. Its rules are `fake-reader` items, `[<lens> |] [<document> |] <rule> [| read <k>]`, where `<lens>` is a lens name or `all`, `<document>` is `strong`, `weak`, `version` or `all`, and leaving either out means every one. The rules are:

- `score <n>`: the reply's score;
- `score containing "<S>" <n>`: the score, only when the document's text contains S. This lets a test rank the anchors blind, by their text, and not by the key;
- `write "<S>" in <FIELD>`, where FIELD is any reply field;
- `omit <FIELD>`.

The score is 5 unless a score rule fires; when several fire, the last in plan order wins. `PRIOR` is `nothing` unless written. Every free-text field is `none` unless written. `read <k>` makes an item apply only to read k of its lens, numbered as in § 4.1. Each fake read costs 1 spend unit, and a `cost` on a fake reader is ignored.

### 5.4 Reply format

Each reply starts with `READ: <read id>` and carries these fields, one per line or block, in the same form as reader-ab.md § 5.4 and its build interpretations (a field starts a line as `FIELD: value`, case-sensitive, and runs to the next field; text before the first field is ignored; a field that appears twice is a failed read):

- `PRIOR`;
- `SCORE`: one integer, of any size and sign, on the scale the lens gives (§ 3.3);
- `STRENGTHS`, `DOUBTS`, `UNDERSOLD`, `OVEREXPLAINED`, `OWNED` and `FLAG-FIXES`, the free-text fields.

From revision 4, when the lens names `criteria`, the reply carries `CRITERION-<name>: <integer>` for each criterion in place of `SCORE`. The read's score is the sum of its criterion scores, computed by the tool. The tool never reads an overall number from the reply: scores in one reply are not independent evidence. A reply missing a criterion, giving one twice, or giving a value that is not an integer is a failed read. A `SCORE` field in such a reply is ignored: the read stands on its criterion fields, and the result counts the replies that carried one (§ 6.1).

The built-in `PROMPT.txt` fixes only this envelope: the `READ`, `PRIOR` and `SCORE` fields and the free-text fields. It states no scale. It tells the reader, for each free-text field, "write exactly `none` if you have nothing material"; that sentence is part of the frozen prompt, so it is covered by the prompt's hash like the rest of the text, and a field that says anything but `none` is flagged (below). From revision 4, for a lens that names `criteria`, the prompt asks for the `CRITERION-<name>` fields in place of `SCORE`; for a lens without criteria it is revision 3's prompt, byte for byte.

A reply missing `READ` is a failed read, and so is a reply, through a lens without criteria, that is missing `SCORE` or whose `SCORE` is not an integer. Failed reads are counted and reported, never guessed. A free-text field is **flagged** when it is present and its value, trimmed, is anything but exactly `none`. A missing or empty field is not flagged.

### 5.5 Blindness

As in reader-ab.md § 5.5: the prompt tells the reader that it knows nothing about the candidate, and any `PRIOR` other than `nothing` is flagged on that read. From revision 3, a reader marked `not-blind` has its reads reported separately and never counted: no rule, gate or flag count includes them. Every verdict line says how many reads it left out for that reason (§ 6.1). A reader's `reader-group`, when given, is reported with its reads, and the result counts valid reads per reader group; a reader group changes no verdict.

## 6. Scoring

Scoring reads only the replies, the key and the frozen plan; for a replicate or an extension, the first run's replies and key as well; and for a plan that names a calibration, the calibration run's. Failed reads, and reads from readers marked `not-blind`, are left out of every denominator below. A rule that needs N of N valid reads is INCONCLUSIVE when the count of valid reads is not exactly N, unless a settled completion lifts it (§ 6.1).

- **The anchor gate**, per lens. It is evaluated only when every planned anchor read of the lens is valid; otherwise it is "not evaluated". It passes when every valid read of the strong anchor scores at or above `anchor-strong-at-least` and every valid read of the weak anchor scores at or below `anchor-weak-at-most`; one read on the wrong side fails it, and the result names each such read with its score. The anchors check that a lens can tell strong from weak; a passed gate doesn't show it could see this version's difference.
- **Calibration** (revision 4). A plan with `calibration-only: yes` reads the anchors through every lens and reads no version; its key file and reads folder hold no version read. Its result gives each lens's calibration: passed when the median of the strong anchor's valid reads is at or above `anchor-strong-at-least` and the median of the weak anchor's valid reads is at or below `anchor-weak-at-most`, the gate's own thresholds, and failed otherwise. A lens may be revised only while no version has been read through it: a revised lens is a new calibration plan that `amends` the earlier one. After the first version read, the lens is frozen, and a revised lens needs a new plan. Naming a calibration is optional. In a run that reads the version and names a calibration, a lens that passed it is calibrated, and a lens that failed it is not counted (below). A run that reads the version and names no calibration reports every lens's scores as uncalibrated. An uncalibrated lens still counts in rules, and in such a run every rule's verdict line, on a lens or `overall`, ends with a tag that says so (§ 6.1).
- **Counted lenses.** A lens whose gate passed is counted, unless it failed a named calibration. A lens whose gate failed or was not evaluated, or that failed a named calibration, is not counted: every rule on it is INCONCLUSIVE with that reason, and its reads of the version are shown but not counted anywhere. One lens's gate voids that lens only.
- **Rules.** A rule's clauses are `PASS if <test> in <k> of <m>`, `PASS if <test> in <k> or more`, and the same with `FAIL`, separated by `; `, ending with `otherwise INCONCLUSIVE`. A test is `score at least <n>`, `score at most <n>`, `<FIELD> flagged` or `<FIELD> not flagged`, where FIELD is a free-text field. A rule on a lens counts that lens's valid reads of the version; an `overall` rule counts the valid reads of the version across every counted lens, and is INCONCLUSIVE when no lens is counted. `<k> of <m>` holds when exactly `<m>` reads are counted and at least `<k>` of them pass the test; `<k> or more` holds when at least `<k>` pass it, however many are counted. Clauses are tried in order, and the first that holds decides. A version cannot be required to beat a score the gate did not show the lens can give: `freeze` rejects (exit `2`, naming the plan line) any `PASS` clause `score at least <n>` where `<n>` is greater than `anchor-strong-at-least`. A `<n>` equal to or below it is accepted, as is any `FAIL` clause. Prefer `<k> of <m>` with slack to unanimity: a unanimity rule (`6 of 6`) fails on one stray read, so it is brittle. The result names rules `r1`, `r2` and so on in plan order, and shows each clause's count.
- **Headroom** (revision 4). For each counted lens, the result compares the median of the strong anchor's valid reads with the median of the version's valid reads. The check needs at least 3 valid reads of the strong anchor on the lens; with fewer, the lens's headroom is not assessed. A rule on a lens whose verdict would be PASS by a `score at least` clause is INCONCLUSIVE instead when the strong anchor's median is not above the version's median, with the reason no headroom, or when the lens's headroom is not assessed, with that reason and the count. An `overall` rule whose verdict would be PASS by a `score at least` clause is INCONCLUSIVE instead when any counted lens has no headroom or has its headroom not assessed, and the reason names those lenses. When a lens has no headroom, the result names a criterion rubric as the next step. The check does not require the rubric. The median of an even count is the mean of the two middle values, and a median that is not whole is printed with `.5`. The check applies to the verdict the rules give, a lifted one included (§ 6.1): a PASS reached by a lift through a `score at least` clause is INCONCLUSIVE when the lens has no headroom. It is not applied inside the completions, which read the rule alone, without the read floor or the gates.
- **Scores** are reported per lens for each document, and for the version per reader as well, with the lowest and highest beside the mean.
- **Flags.** For each lens and free-text field, the result reports how many valid reads of the version flagged it.
- **Read floor.** When the plan sets `min-valid-reads`, a rule that counts fewer valid reads than the floor is INCONCLUSIVE, with the reason "below the read floor".
- **Replicates.** A replicate's result gives, for each clause of each rule, the first run's and this run's counts (`k` of `n` counted reads passing the test) and the two-sided Fisher exact p-value for the difference. Known limit: each replicate is compared with the first run only.

### 6.1 Evidence beside the verdicts

Nothing in this section changes a verdict, except the lift (under Missing reads). Each line is reported beside the verdicts above, which come from the frozen rules alone (§ 8).

- **Interval.** For each clause of each rule, `n` is the number of reads the rule counts and `k` the number that pass the clause's test. The result gives the 95% Wilson score interval for `k/n`, with z = 1.959964. When `n` is 0, no interval is computed, and the line says so.
- **Against a declared share.** When a rule names a `null-share` q, each clause also gets an exact p-value from the binomial distribution with `n` trials and chance q: under `greater`, the chance of `k` or more; under `less`, of `k` or fewer; under `two`, twice the smaller of the two, and at most 1. Without a `null-share`, no p-value is printed: a single version has no natural share to test against.
- **Missing reads.** For each lens, the result counts the planned reads of the version that are missing: failed, and not run. For each rule with missing reads among the reads it would count, the rule is evaluated again under every completion of those reads, each missing read taking any score and any set of flagged fields, as if every planned read of the version were valid. The result says whether one verdict holds under every completion (settled) or which verdicts are possible (unsettled). Missing anchor reads are not completed: the gate stays "not evaluated", and a lens that is not counted adds no reads to complete. **The lift.** It changes a verdict in one case only: when the plan sets `min-valid-reads`, the rule counts at least that many valid reads, the rule is INCONCLUSIVE because of its clauses alone (not a gate, no counted lens, the floor, no headroom or headroom not assessed, or a lens that failed its calibration), and one verdict holds under every completion, that verdict replaces INCONCLUSIVE, and the result says it was lifted. Without a read floor nothing is lifted.
- **A dead run.** When no read in the run is valid, the result says so in one line. The exit status is `1`, as for any run with a failed read (§ 7).
- **The top of the scale.** For each lens, the result gives the version's lowest valid score beside the strong anchor's highest valid score, and the version's spread (highest minus lowest). When the version's lowest score is at or above the strong anchor's highest, the lens cannot rank the version above the strong anchor, and the result says so. When every valid read gives the version the same score, the result says so. When the lens names `max`, the result gives the room between the strong anchor's highest score and that maximum.
- **Not-blind reads.** Each rule's verdict line carries the number of reads it left out because their reader is marked `not-blind` (§ 5.5).
- **What the reads stand for.** Every result carries one validity line: the readers are models standing in for human screeners, that stand-in has not been checked against human ratings, and reads from one model and prompt may not be independent, so each p-value assumes independence and may be too small. Each p-value carries a short form of the same caveat on the same line.

#### Printed forms

`<rule>` is the rule's name (`r1`, `r2` and so on), `<arm>` is the lens's arm (`l1`, `l2` and so on), and `<test>` is the clause's test as written. A p-value is printed rounded half up to 4 decimal places, or as `< 0.0001` when it rounds to 0. An interval's lower end is rounded down and its upper end rounded up, to 3 decimal places. `<side>` is `two-sided`, `one-sided greater` or `one-sided less`.

- `rule <rule> evidence: <test>: <k> of <n> counted reads; 95% interval <lo> to <hi>`, one line per clause, or `... <k> of <n> counted reads; interval not computed` when `n` is 0.
- With a `null-share` q, written as the plan wrote it, the same line gains, before the interval: `; p = <p> <side> against <q> (reads may be correlated; may be too small)`.
- `missing <arm> version: <m> of <planned> planned reads (failed <f>, not run <r>)`, one line per lens.
- `rule <rule> completions (missing reads: <m>): settled: <verdict>`, or `... unsettled: <verdicts> possible`, in the order PASS, FAIL, INCONCLUSIVE, separated by `, `. A rule with no missing read among those it would count gets no completions line.
- `DEAD: 0 of <N> planned reads are valid`, where `N` counts every planned read of every lens.
- `scores <arm> version against strong anchor: lowest version score <a>, highest strong-anchor score <b>`, or `... not assessable` when either has no valid read.
- `scores <arm> version spread: <s> (highest <h>, lowest <l>)`, or `scores <arm> version spread: not assessable` with no valid read of the version.
- When `a` is at or above `b`: `scores <arm>: the version scores at or above the strong anchor; this lens cannot rank it higher`.
- When the version has two or more valid reads and its spread is 0: `scores <arm>: every read gives the version the same score`.
- When the lens names `max`: `scores <arm> room above the strong anchor: <max minus b> (scale maximum <max>)`.
- Every rule verdict line carries ` [not blind: <b> reads left out]`. From revision 4, in a run that reads the version and names no calibration, ` [uncalibrated]` follows it and ends the line.
- `rule <rule> reason: below the read floor (<v> counted reads, floor <f>)`.
- After a lift, the verdict line gives the lifted verdict, and the reason line reads `rule <rule> reason: lifted from INCONCLUSIVE: settled under every completion of <m> missing reads; read floor <f> met`.
- In a replicate: `replicate of: <first freeze sha256>`, and per clause `rule <rule> replicate: <test>: first run <k1> of <n1>, this run <k2> of <n2>; Fisher exact p = <p> two-sided`.
- `reader-group <name>: <v> valid reads`, one line per reader group named in the plan, counting its valid reads across every lens.
- From revision 4:
  - in the header: `anchor strong: written by <who>` and `anchor weak: written by <who>`, each followed by `; note: <text>` when the anchor has a note, and, per lens, `<arm> author edited the version: <yes|no>`;
  - `headroom <arm>: strong anchor median <a>, version median <b>`, then `headroom <arm>: none; next step: a criterion rubric` when `a` is not above `b`;
  - `headroom <arm>: not assessed (<v> valid strong-anchor reads, at least 3 needed)`, in place of those lines when the lens has fewer than 3;
  - on a rule on a lens: `rule <rule> reason: no headroom (strong anchor median <a>, version median <b>)`, or `rule <rule> reason: headroom not assessed (<v> valid strong-anchor reads, at least 3 needed)`;
  - on an `overall` rule: `rule <rule> reason: no headroom on <arms>; headroom not assessed on <arms>`, where `<arms>` lists those lenses in plan order, separated by `, `, and either part is left out, with its `; `, when it names no lens;
  - per lens that names `criteria`: `criteria <arm>: <c> replies carried a SCORE field, not read`;
  - in a calibration run, per lens: `calibration <arm>: passed (strong median <a>, weak median <w>)` or `calibration <arm>: failed (strong median <a>, weak median <w>)`, and the line `calibration only: no version read`;
  - in a run that names a calibration: `calibration: <the calibration's freeze sha256>`, and, on a rule on a lens that failed it, `rule <rule> reason: <arm> failed its calibration`;
  - in a run that reads the version and names no calibration: `calibration: none; scores are uncalibrated`;
  - in an extension: `extends: <first freeze sha256>; the sample size changed after a result was seen`, and per rule `rule <rule> extension: first run <verdict>, pooled <verdict>`.
- `validity: the readers are models standing in for human screeners, and that stand-in has not been checked against human ratings. Reads from one model and prompt may not be independent, so each p-value assumes independence and may be too small.`

## 7. Output and exit status

`track-record panel score` writes a result file containing:

- the plan and freeze hashes, any amendment's, the prompt hash, and each lens's name, file and hash;
- the version, the anchors and the thresholds;
- the key;
- one row per read: reader, document, score, flagged fields and flags;
- per lens: its read counts, its anchor gate with the scores or the reads that failed it, whether it is counted, its scores and its flag counts;
- the counted lenses;
- each rule, with its clause counts, its verdict and any reason;
- the spend tally, failed reads and any cut;
- the evidence lines of § 6.1: each clause's interval and any p-value, the missing reads per lens and each rule's completions, the score lines per lens, any `DEAD` line, and the validity line;
- any read-floor or lift reason, the counts per reader group, and, in a replicate, the comparison with the first run;
- from revision 4: who wrote each anchor and each lens's author-edited disclosure in the header, the calibration line, each lens's headroom lines, the count of unread `SCORE` fields per lens that names criteria, and, in an extension, the first run's verdicts beside the pooled ones.

Every run writes a new result; an earlier result is never overwritten.

Exit status, as in `ab`:

- `0`: the run completed and was scored, whatever the verdicts, or it was a print without `--live`.
- `1`: the run completed, but at least one read failed or the run was cut.
- `2`: the run could not run: a hash mismatch, a failed document check, a missing input, a freeze over an existing freeze or run, a plan error, or a run that stopped early.

When causes combine, the higher code wins.

## 8. Rules that hold in every run

- No read before a freeze, and no plan or lens edit after one.
- Every lens reads both anchors in every run, before it reads the version.
- The document check runs before any read.
- A reader never learns which document it is reading.
- Verdicts come from the frozen rules only. The tool has no option to change a rule, a threshold or a lens at scoring time.
- A lens is revised only before any version is read through it (§ 6, Calibration). An extension changes the sample size only, and reads each count at its share of the pooled planned reads; an amendment never changes a threshold, and restates a count only at the same share.
- The evidence of § 6.1 sits beside the verdicts and never changes one, except the lift, which only a plan with a read floor allows.
- Reads from a reader marked `not-blind` are never counted in a rule, a gate or a flag count.
- A reader's suggested rewrite is reported as text and applied to nothing.

## 9. Decisions

Decisions 1 to 10 were settled as written when the owner signed revision 1 on 2026-11-05; each "Default" below is the settled choice. Decisions 11 to 13 were settled on 2026-11-05 for revision 2.

1. **Command name.** Default: `track-record panel`, with `freeze`, `run` and `score`, as `ab` has.
2. **How a lens is defined.** Default: a plain-text prompt file per lens, named in the plan, its sha256 frozen with the plan, handed to the reader unchanged as `LENS.txt` beside the built-in `PROMPT.txt`. Alternative considered: lens text written inline in the plan. The file keeps a lens reusable across plans and keeps the plan short.
3. **The anchor thresholds.** Default: two required plan fields, `anchor-strong-at-least` and `anchor-weak-at-most`, whole numbers with the first greater than the second. Every valid anchor read must land on its side; the mean is not used, because a mean can hide one read that got an anchor backwards.
4. **One failed anchor voids what.** Default: that lens only. The other lenses keep their own gates and verdicts; an overall rule counts only counted lenses.
5. **How a pass condition is written.** Default: per-lens and overall rules in `ab`'s clause language, with `PASS` and `FAIL` in place of `SUPPORTED` and `REFUTED`, over scores and flagged fields (§ 6). Alternative considered: keeping `SUPPORTED` and `REFUTED`; `PASS` and `FAIL` were chosen because a single version has a pass condition, not a hypothesis about a difference.
6. **Anchor read counts.** Default: `anchor-reads-per-reader` is its own field, default 1, so that anchors cost one read per reader per lens while the version keeps `reads-per-reader` (default 3). (Superseded in revision 4 by decision 23, which makes the default 2.)
7. **Read order within a lens.** Default: strong anchor, weak anchor, then the version, each reader in turn, so that a cut by the spend ceiling leaves the gate evaluable.
8. **What "flagged" means.** Default: a free-text field is flagged when it says anything but exactly `none`; a missing or empty field is not flagged. No pattern matching over fields in draft 1 (the `mechanisms` of `ab` could be added later as a rule test).
9. **Reserved lens names.** Default: `all`, `overall`, `strong`, `weak` and `version` may not name a lens, because the plan's `rules` and `fake-reader` items use them.
10. **Not-blind readers.** Default: reported as in `ab`, flagged on each read and counted separately on the version; the gate does not treat them apart. No rule can leave them out of `overall` in draft 1 (§ 5.5).
11. **Evidence.** Each clause count gets a Wilson interval. A rule may name a `null-share` at freeze, and then each clause gets an exact p-value against it; without one, no p-value is printed.
12. **Missing reads and the top of the scale.** The completions are reported only; they lift no INCONCLUSIVE (superseded in revision 3 by decision 16, the lift). A dead run keeps exit `1` and gains the `DEAD` line. The score lines report a version at or above the strong anchor, a version with no spread, and, when a lens names its maximum, the room above the strong anchor.
13. **Not-blind reads** still count in revision 2, and every verdict line says how many there are.

Proposed for revision 3, settled when the owner signs it:

14. **Replicates.** A replicate is a new run folder that names the first run's freeze; repeat reads inside one folder are not offered.
15. **Not-blind readers.** From revision 3 their reads are never counted, which changes the verdicts of plans that have one. This replaces decision 10's "no rule can leave them out".
16. **The lift.** A settled completion lifts an INCONCLUSIVE only when the plan sets a read floor and the rule meets it.

Proposed for revision 4, settled when the owner signs it:

17. **Headroom, not reachability.** The anchor gate already keeps the strong anchor above every pass bar. The headroom check asks a different question: does the instrument have room above the version under test? It compares the strong anchor's scores with the version's over several reads, at least 3 of the strong anchor, and it acts: a higher-score PASS with no headroom, or with too few strong-anchor reads to assess it, is INCONCLUSIVE, and the result points to a criterion rubric. An `overall` rule needs headroom on every lens it counts.
18. **Criterion scores are summed by the tool**, never read as an overall number from the reply. A `SCORE` field beside them is ignored and counted: failing the read would throw away a valid set of criterion scores for a habit of the reader. Only a lens with criteria gets a changed prompt; a lens without them gets revision 3's, byte for byte.
19. **Who wrote each anchor** is a required fixed set (`user`, `model`, `third-party`, `unknown`), naming every model family that wrote or edited any of it when it is `model`, and an optional note, last on its line.
20. **Calibration** is an anchors-only run before any version is read, optional in revision 4, because requiring it would refuse every plan written so far. It passes on the gate's own thresholds: a second pair of bars would be a second thing to tune after seeing reads. A lens may be revised only while no version has been read; after that it is frozen and a revised lens is a new plan. No calibrated score is reported unless the calibration passed. A lens with no calibration still counts, its scores labelled uncalibrated; a lens that failed the named calibration is not counted.
21. **The author-edited disclosure** is per lens, required, about the version only, written into the freeze file and printed beside each lens in the result header. It changes no verdict.
22. **Sample size only, never the threshold.** As reader-ab.md decision 24: the sample size is reads per reader, readers of the same models and replicates; everything else is not, and a change to it is refused at freeze. A rule's count is part of its threshold, as a share, so an amendment that changes the read count restates the count at the same share, and an extension reads each count at its share of the pooled planned reads, so that a `<k> or more` rule does not get easier as reads pool. A plan frozen under an earlier revision is never rescored under this one.
23. **Two anchor reads per reader.** `anchor-reads-per-reader` defaults to 2, so that the headroom check has its several reads: two readers give 4 reads of each anchor per lens, which meets the minimum of 3. The default run makes twice the anchor reads it did, and the anchor gate, which fails on one read on the wrong side, has twice the reads that can fail it. A default of 3 was considered and set aside: a lens that misreads 5 percent of anchor reads passes the gate about 66 percent of the time with 8 anchor reads (0.95 to the 8th), and about 54 percent with 12 (0.95 to the 12th), too many false INCONCLUSIVE lenses for what the headroom check needs. The gate rule itself does not change. With one blind reader the default gives 2 strong-anchor reads, headroom is not assessed, and the plan must ask for more.

## Build notes (draft 1)

### The plan file

This example is invented:

```
posting: posting.txt
version: resume.txt
anchors:
  strong | anchor-strong.txt | written-by user
  weak | anchor-weak.txt | written-by user
lenses:
  recruiter | recruiter.lens.txt | author-edited-version no
  hiring-manager | hiring-manager.lens.txt | author-edited-version no
readers:
  reader-1 | fake
  reader-2 | /path/to/my-reader.sh --model small | cost 3
reads-per-reader: 3
anchor-reads-per-reader: 2
anchor-strong-at-least: 7
anchor-weak-at-most: 4
rules:
  recruiter | PASS if score at least 7 in 5 of 6; FAIL if score at most 4 in 2 or more; otherwise INCONCLUSIVE
  hiring-manager | FAIL if DOUBTS flagged in 3 or more; PASS if score at least 7 in 5 of 6; otherwise INCONCLUSIVE
  overall | PASS if score at least 7 in 10 or more; otherwise INCONCLUSIVE
spend-ceiling: 56
fake-reader:
  strong | score 9
  weak | score 2
  version | score 7
  hiring-manager | version | write "no numbers" in DOUBTS | read 9
```

- **Readers, scalars and paths** follow reader-ab.md's build interpretations: `cost`, `spend-ceiling` and `read-timeout` are whole numbers, 0 or more; `reads-per-reader` and `anchor-reads-per-reader` are 1 or more; a live command is split by POSIX shell-word rules and its program is an absolute path or a name on `PATH`; file paths are relative to the plan's folder.
- **Rules** always start with their lens or `overall`, even with one lens.
- **Where errors are found.** Every plan error is found by `freeze`, which names the plan line number where there is one and writes no freeze file. `run` re-checks the hashes, compares the built-in prompt's sha256 with the frozen one, and runs the document check, before any read.
- **One run to a folder, the run log, the key's hash, errors on files in the run folder, a stopped run, an interrupt and escaped output** all follow reader-ab.md's build interpretations and other rulings, unchanged. The key file has three tab-separated fields: the read id, the reader and the document.

### Live readers

As in reader-ab.md's build interpretations, with the read folder holding exactly `DOCUMENT.txt`, `LENS.txt`, `POSTING.txt` and `PROMPT.txt` when the command starts. Read k of a lens is at `reads/<arm>/<k>/`, where `<arm>` is `l1`, `l2` and so on. Results name a read as `<arm>/<k>`, for example `l2/5`. The prompt is built into the tool and fixed per tool version; it is not the `ab` prompt, and its sha256 goes into the freeze file and the result.

### Known limits

- The known limits of `ab`'s live readers hold here: a reader's standard output and standard error are held in memory with no size limit, and a timeout stops the reader's own process only.
- A lens is handed to the reader as text. Whether the reader takes the role is up to the reader; the gate measures only whether it ranked the anchors.
- Two anchors fix two points on a scale. A lens that ranks them correctly can still be wrong about the version; the gate rules out a lens that cannot see, not one that sees badly. More anchors, or anchors closer to the version, are a change for a later revision.
- Set the strong threshold at or above the score the version must reach.
- The ceiling stops reads once the tally reaches it, so one costly read can overshoot it, the same as in `ab`.

A reader's model is its command and options (`not-blind`, `cost` and `reader-group`) without its name, except that a fake reader's `cost` is never kept, because the tool ignores it, so an extension may change it; the extension's set of models must equal the first plan's, and a reader name both plans use must name the same model. Every input the first freeze recorded must have that hash now. Refusals: `an extension may change only reads-per-reader, anchor-reads-per-reader and the number of readers of each model: <setting>`, `changed since the first freeze: <file>`, `the first plan is missing: …`, `extends must name a first run, not an amendment, a replicate, an extension or a calibration: …`, `extends must name a .freeze file`, `a plan may not carry extends with amends or replicate-of`, and `the first run already has an extension: <folder>`, found by looking beside the extension's own folder. Each count of each rule (`<k>`, and `<m>`) is multiplied by the pooled planned counted reads over the first plan's; a result that is not whole gives, at `freeze`, `an extension's pooled reads give no whole number for <rule name>`. The result prints `rule <rule> (<label>) at the pooled reads: <the rule with its counts restated>` and `rule <rule> (<label>) extension: first run <verdict>, pooled <verdict>`, where the first run's verdict is the one its own result gives. Gates, calibration, headroom, rules, completions and the read floor read the pooled blind reads, and the verdict line counts the not-blind reads of both runs; the key, the per-read rows, the `reads` lines, the `missing` lines, the score lines, the flag counts and the `criteria` line show this run's reads. `run` and `score` stop with `the first run has not been run yet: …` when the first folder holds no key, and write nothing there.
26. **The earlier answers.** The goldens of release 0.7.0 are rewritten as revision 4 results of their plans, with the two required fields added and their anchor read count unchanged. A verdict they held that headroom changes is a PASS made INCONCLUSIVE with a headroom reason, and no other difference is accepted.
27. **The count of unread `SCORE` fields.** The `criteria <arm>` line counts every reply of a blind reader's read of that lens, every document, valid or failed, that holds a `SCORE` field. A read with no reply, not run or written by a reader that wrote nothing, is not a reply.
28. **A `SCORE` field twice.** The repeated-field rule is general: any field that appears twice, `SCORE` included, makes the read a failed read (`SCORE appears twice`), so a criteria reply with `SCORE` twice loses its criterion fields. It cannot overstate a result and loses one read at most. The reply still holds a `SCORE` field, so point 27 counts it.
29. **Headroom and a lifted PASS reached through more than one clause.** A lifted PASS is settled by every completion of the missing reads, and different completions may reach PASS through different clauses. The verdict is made INCONCLUSIVE by a headroom reason when at least one completion that reaches PASS does so through a `PASS if score at least` clause; a lifted PASS that every completion reaches through a flagged-field clause is left alone. This is the reading that cannot overstate a PASS.
30. **Plan-line details.** A lens field `max` with no value gives revision 3's `a lens's max is a whole number:` message with an empty text. A calibration-only plan that carries `rules` is refused on the first rule's line, or on the `calibration-only` line when `rules` has no item. `calibration`, `calibration-only` and `extends` are read when the plan is parsed, and their checks that need the files they name are made by `freeze`, `run` and `score`.
31. **The plan a refusal names.** A refusal about an earlier plan (`the calibration plan is missing: …`, `the amended plan is missing: …`, `the first plan is missing: …`, `changed since the freeze: …`, `calibration must name a calibration-only run: …`, `extends must name a first run, …: …` and the `cannot be read under revision 4` messages) ends with that plan's file as the plan's own line writes it, in the folder the line names and without `.freeze`, for example `../first/plan.txt`, as in `track-record ab`.
